# Sunshine Alley Launcher V3 — Command-Line Reference

Source reviewed: `feature/cross-platform-gui`, archive commit `199fa88066b97a2b9d64cf44957c0bdd6fcbaf68`  
Reference created: 20 August 2026

This document covers the command-line and publishing options implemented in the reviewed V3 branch.

## Quick reference

V3 contains two executables:

| Executable | Purpose |
| --- | --- |
| `SunshineAlleyLauncher` / `SunshineAlleyLauncher.exe` | Avalonia GUI; Windows and Linux installation/repair/uninstall and launcher self-update |
| `sunshine-alley-cli` / `sunshine-alley-cli.exe` | Headless diagnostics, server listing, modpack synchronization, and Valheim launching |

Important distinctions:

- `sunshine-alley-cli launch` synchronizes the selected **modpack** before launching.
- It does **not** update the V3 launcher executable.
- Launcher self-update currently runs only through an installed Windows or Linux GUI executable.
- `launch --dry-run` can still download and delete modpack files; it only prevents Valheim from starting.
- Only top-level CLI help works. Do not run `launch --help`, because it is ignored and may result in a vanilla launch.

## Requirements and supported targets

The source targets .NET 10 and supports:

| RID | Platform |
| --- | --- |
| `win-x64` | Windows x64 |
| `linux-x64` | Linux x64 |
| `osx-x64` | Intel macOS |
| `osx-arm64` | Apple Silicon macOS |

## Restore, build, and test

From the repository root:

```bash
dotnet --info
dotnet restore "Sunshine Alley Launcher.sln"
dotnet build "Sunshine Alley Launcher.sln" -c Release --no-restore
dotnet run --project tests/SunshineAlley.SmokeTests/SunshineAlley.SmokeTests.csproj -c Release --no-restore
```

## Publish everything

The included scripts restore, run smoke tests, publish both executables for all four RIDs, and create archives plus the raw directly downloadable Linux launcher.

Linux/macOS:

```bash
./scripts/publish-all.sh
```

PowerShell:

```powershell
./scripts/publish-all.ps1
```

Output:

```text
artifacts/publish/<RID>/app/     GUI application
artifacts/publish/<RID>/tools/   CLI executable
artifacts/packages/              Packaged releases
```

## Publish one GUI target

```bash
dotnet publish src/SunshineAlley.App/SunshineAlley.App.csproj \
  -c Release \
  -r win-x64 \
  --self-contained true \
  -p:PublishSingleFile=true \
  -p:IncludeNativeLibrariesForSelfExtract=true
```

Replace `win-x64` with `linux-x64`, `osx-x64`, or `osx-arm64` as needed.

The raw GUI executable is named `SunshineAlleyLauncher` (`.exe` on Windows). The Windows installer places the registered copy at the canonical name `Sunshine Alley Launcher.exe`. Linux installs the raw name at the resolved XDG path `.../sunshine-alley/launcher/SunshineAlleyLauncher`.

## Publish one CLI target

```bash
dotnet publish src/SunshineAlley.Cli/SunshineAlley.Cli.csproj \
  -c Release \
  -r win-x64 \
  --self-contained true \
  -p:PublishSingleFile=true \
  -p:IncludeNativeLibrariesForSelfExtract=true
```

The published executable is `sunshine-alley-cli` (`.exe` on Windows).

## GUI application options

Development invocation:

```bash
dotnet run --project src/SunshineAlley.App/SunshineAlley.App.csproj -- [options]
```

Published invocation:

```powershell
.\SunshineAlleyLauncher.exe [options]
```

### User-facing GUI options

| Option | Behaviour |
| --- | --- |
| No arguments | Starts normally. On Windows/Linux, an uninstalled copy opens setup; the fixed installed copy opens the launcher. |
| `--portable` | Bypasses the Windows/Linux installed-copy requirement and opens the GUI directly. Intended for development. |
| `--repair` | Opens the Windows/Linux setup window in repair mode. |
| `--uninstall` | Opens the Windows/Linux uninstall UI. Removal still requires confirmation in the window. |

Examples:

```bash
dotnet run --project src/SunshineAlley.App/SunshineAlley.App.csproj -- --portable
```

```powershell
& "$env:LOCALAPPDATA\Sunshine Alley\App\Sunshine Alley Launcher.exe" --repair
& "$env:LOCALAPPDATA\Sunshine Alley\App\Sunshine Alley Launcher.exe" --uninstall
```

```bash
"${XDG_DATA_HOME:-$HOME/.local/share}/sunshine-alley/launcher/SunshineAlleyLauncher" --repair
"${XDG_DATA_HOME:-$HOME/.local/share}/sunshine-alley/launcher/SunshineAlleyLauncher" --uninstall
```

`--portable` does not create an isolated portable data layout. It only bypasses the installed-copy check. Normal platform configuration and data locations remain in use, and launcher self-update remains disabled because the process is not the registered executable.

### Internal GUI options

These are generated by the installer/updater and should not be invoked manually:

| Option | Internal purpose |
| --- | --- |
| `--update-helper <plan>` | Protected Windows/Linux executable replacement helper |
| `--post-update <plan>` | Confirms successful startup after replacement |
| `--update-rollback <plan>` | Restarts and records a rolled-back update |
| `--maintenance-helper <plan>` | Performs protected uninstall (and Windows legacy cleanup) |
| `--wait-for-pid <pid>` | Waits for an earlier launcher process to exit |
| `--cleanup-legacy-file <path>` | Removes an approved V2 or temporary launcher file |

`--simulate-update-startup-failure` is a rollback test hook. It only exists in development builds compiled with `AllowUnsignedUpdates=true` and has no effect in normal production builds.

## Headless CLI

Development invocation:

```bash
dotnet run --project src/SunshineAlley.Cli -- <command> [options]
```

Published invocation:

```powershell
.\sunshine-alley-cli.exe <command> [options]
```

```bash
./sunshine-alley-cli <command> [options]
```

### CLI commands

| Command | Purpose |
| --- | --- |
| `help`, `--help`, `-h` | Prints top-level help |
| `doctor` | Diagnoses Steam, Valheim, BepInEx, Doorstop, and launch readiness |
| `servers` | Fetches and prints available server profiles |
| `verify` | Synchronizes and verifies a positive modpack ID |
| `launch` | Synchronizes a positive modpack and launches Valheim |
| `device-id` | Prints the launcher device identity |

## Help

```bash
dotnet run --project src/SunshineAlley.Cli -- --help
dotnet run --project src/SunshineAlley.Cli -- help
dotnet run --project src/SunshineAlley.Cli -- -h
```

Only top-level help is implemented. This is unsafe:

```bash
sunshine-alley-cli launch --help
```

The current parser silently ignores `--help` there and may proceed with the default vanilla launch.

## `doctor`

```text
doctor [--modpack ID] [--game PATH] [--data PATH] [--no-steam] [--persistent]
```

Example:

```bash
dotnet run --project src/SunshineAlley.Cli -- doctor \
  --modpack 1 \
  --game "/path/to/Valheim" \
  --data "/path/to/launcher-data"
```

It reports:

- OS and runtime identifier;
- device identity source and fallback status;
- Steam root and detected Valheim build;
- game executable;
- BepInEx preloader;
- native Doorstop payload;
- required Unix Steam launch option;
- detected problems; and
- final `READY` or `NOT READY` state.

`doctor` does not synchronize or download the modpack. Defaults are vanilla (`-99`), saved/discovered game path, saved/default data path, Steam enabled, and persistence disabled.

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Ready |
| `2` | Not ready |
| `1` | Exception or initialization/API failure |

## `servers`

```bash
dotnet run --project src/SunshineAlley.Cli -- servers
```

It contacts the API, applies the authenticated-device visibility rules, and prints records similar to:

```text
World Name | modpack=1 | steam-build=12345678
```

It also adds:

```text
Private World | modpack=-1
Vanilla / No mods | modpack=-99
```

Exit code `0` means success; runtime or API failures return `1`.

## `verify`

```text
verify --modpack ID [--data PATH]
```

Example:

```bash
dotnet run --project src/SunshineAlley.Cli -- verify \
  --modpack 1 \
  --data "/path/to/launcher-data"
```

The modpack ID must be positive. `verify`:

1. Validates the data directory.
2. Refreshes server/device authorization.
3. Hashes the existing files.
4. Sends the local file list to the API.
5. Deletes server-reported illegal or obsolete files.
6. Downloads missing or changed files.
7. Applies saved optional-mod selections.
8. Installs default configurations.
9. Rechecks up to four times.
10. Succeeds only when the server accepts the resulting layout.

Modpacks are stored under:

```text
<data>/ModPacks/<ID>/
```

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Verified successfully |
| `2` | Missing or non-positive modpack ID |
| `1` | API, filesystem, security, or synchronization failure |

## `launch`

```text
launch [--modpack ID] [--game PATH] [--data PATH] [--no-steam] [--persistent] [--dry-run]
```

Example:

```bash
dotnet run --project src/SunshineAlley.Cli -- launch \
  --modpack 1 \
  --game "/path/to/Valheim" \
  --data "/path/to/launcher-data"
```

For a positive modpack ID, `launch` performs this sequence:

1. Loads settings and device identity.
2. Validates the data directory.
3. Refreshes servers.
4. Verifies and synchronizes the modpack.
5. Diagnoses the game layout.
6. Deploys Doorstop/BepInEx launch support.
7. Starts Valheim.
8. Waits for Valheim to exit.
9. Restores the original launch state unless `--persistent` is set.

### Launch options

| Option | Meaning |
| --- | --- |
| `--modpack ID` | Selects a modpack/profile |
| `--game PATH` | Overrides the Valheim installation directory |
| `--data PATH` | Overrides the launcher/modpack data directory |
| `--no-steam` | Bypasses Steam's URI launch and starts the executable/wrapper directly |
| `--persistent` | Leaves the selected injection configuration active after Valheim exits |
| `--dry-run` | Synchronizes and diagnoses, but does not deploy into the game directory or start Valheim |

Modpack/profile IDs:

| ID | Behaviour |
| --- | --- |
| Positive | Server modpack; synchronized before launch |
| `-1` | Private World |
| `-99` | Vanilla/no mods; also the default |
| `0` | Unmanaged/cleanup behaviour; not documented as a public profile |

A positional numeric ID also currently works, for example `launch 1`, but `--modpack 1` is clearer.

### Warning about `--dry-run`

`--dry-run` is not non-mutating. Before stopping, it can:

- contact the API;
- synchronize the modpack;
- download missing files;
- delete illegal or obsolete files; and
- update default configuration files.

It does not deploy the modpack into the game directory or start Valheim. A better description is “verify and diagnose without launching.”

### Meaning of `--no-steam`

`--no-steam` bypasses the Steam launch URI. It still calls `EnsureRunningAsync()`, so it does not mean that Valheim will run with the Steam client completely closed.

### Meaning of `--persistent`

Without persistence, Sunshine Alley restores the original launch state after Valheim exits.

With persistence:

- Windows retains the deployed Doorstop configuration/files.
- Linux/macOS retains the modded launch wrapper.
- Subsequent launches may continue using the chosen modded environment.

### Platform behaviour

Windows deploys `winhttp.dll`, `doorstop_libs`, and `doorstop_config.ini`, and restores the original state after exit unless persistent mode is selected.

Linux/macOS generates `sunshine-alley-launch.sh`. Steam must be configured once to invoke it; `doctor` prints the exact required launch option. Without persistence, the wrapper is changed to safe pass-through mode after exit.

## `device-id`

```bash
dotnet run --project src/SunshineAlley.Cli -- device-id
```

This prints the device identity. Runtime initialization can create configuration directories, a fallback identity, and RSA identity material in the platform secret store.

Exit code `0` means success; identity or secret-store initialization failures return `1`.

## Default storage locations

| Platform | Configuration | Data/modpacks |
| --- | --- | --- |
| Windows | `%LOCALAPPDATA%\Sunshine Alley\Config` | `%LOCALAPPDATA%\Sunshine Alley\Data` |
| Linux | `${XDG_CONFIG_HOME:-$HOME/.config}/sunshine-alley/launcher` | Default: `${XDG_DATA_HOME:-$HOME/.local/share}/sunshine-alley/data` |
| macOS | `~/Library/Application Support/Sunshine Alley/Launcher` | Same application-support directory |

Saved settings are stored in `settings.json`.

## Launcher updates versus modpack updates

| Capability | GUI | CLI |
| --- | ---: | ---: |
| Verify/download modpack files | Yes | Yes |
| Launcher executable self-update | Windows and Linux | No |
| Automatic launcher check at startup | Installed Windows/Linux GUI | No |
| Signed update-manifest verification | Yes | Not exposed |
| Automatic failed-update rollback | Yes | Not exposed |

The GUI's launcher self-update requires all of the following:

- Windows or Linux;
- execution from the platform's validated installed launcher;
- a valid configured update channel;
- valid API-envelope and manifest signatures;
- a valid package SHA-256 hash; and
- on Windows, a valid Authenticode signature/publisher.

Linux additionally applies executable permissions, stages under XDG cache, copies to the application filesystem, atomically renames the verified replacement, and retains a verified rollback executable until startup confirmation. macOS currently reports that automatic application updates are not enabled.

The optional signed `minimumSupportedVersion` field disables Play when the running GUI version is lower. The highest signed value seen per channel/RID is remembered across restarts and cannot be lowered by replaying a null/lower policy. This is distinct from `minimumVersion`, which describes update-package/bridge compatibility.

## Missing headless launcher self-update

The branch does not currently implement any of these:

```text
sunshine-alley-cli update
sunshine-alley-cli self-update
SunshineAlleyLauncher.exe --update-only
```

Adding `runtime.Updates.CheckAndLaunchAsync()` directly to the CLI is insufficient because the update service requires the current process to be the registered GUI launcher executable. A separate CLI executable fails that check.

A suitable implementation would add a headless GUI-executable mode:

```powershell
& "$env:LOCALAPPDATA\Sunshine Alley\App\Sunshine Alley Launcher.exe" --update-only
```

That mode should skip Avalonia, create `LauncherRuntime`, call `Updates.CheckAndLaunchAsync`, report progress, and return meaningful exit codes. A script could then update the launcher before invoking the CLI game launch command.

## Current parser and behavioural caveats

- Only top-level help works.
- `launch --help` is ignored and may launch vanilla.
- Unknown options are silently ignored.
- Missing option values are not explicitly reported.
- Any numeric positional argument can become the modpack ID.
- `launch --dry-run` still modifies/synchronizes modpack data.
- CLI launch does not perform the GUI's server-versus-local Steam build compatibility check.
- The CLI cannot enable or disable optional mods.
- The CLI cannot self-update the launcher executable.

These are the main areas to tighten before treating the CLI as a polished public end-user interface.
