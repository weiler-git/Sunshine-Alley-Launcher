# Sunshine Alley Launcher V3 update API deployment

This document defines the new launcher-update API contract and release-storage layout. It is deliberately separate from the legacy V2 updater. Do not change, redirect, or remove `LauncherCheckUpdate` while V2 clients remain in circulation.

The API/backend source was not part of the supplied launcher repository, so this patch does not pretend to modify it. This is the implementation contract and operator runbook for adding the handler to the existing backend while preserving its current authentication and V2 behavior.

## 1. Compatibility boundary

Maintain both operations:

| Operation | Client | Response contract | Release file |
| --- | --- | --- | --- |
| `LauncherCheckUpdate` | WinForms V2 | Literal `OK` or a direct raw Windows EXE URL | Long-lived V3 bridge EXE |
| `LauncherGetUpdateV3` | Avalonia V3+ | JSON signed-envelope object described below | RID/channel-specific signed release |

The V2 operation must never return a ZIP, Linux artifact, macOS artifact, or V3 JSON response. Existing V2 clients only know how to download a raw executable and move it into their old canonical path.

For initial development, leave `LauncherCheckUpdate` completely untouched. Exercise V3 updates through a `development` channel on the new operation.

## 2. Request transport and authentication

V3 uses the same signed form POST transport as the existing launcher API:

```text
POST /valheimapi?Exec=LauncherGetUpdateV3
Content-Type: application/x-www-form-urlencoded

jsonData=<exact JSON request>
sender=launcher:<device-id>
signature=<player RSA signature over the exact jsonData string>
```

Apply the same sender parsing, device public-key lookup, signature verification, request-size limit, rate limiting, and audit policy used by `LauncherServerList` and `LauncherVerifyFiles`.

The decoded request JSON is:

```json
{
  "Version": "3.0.0",
  "RuntimeIdentifier": "win-x64",
  "Channel": "development",
  "ExecutableHash": "64 lowercase hex characters",
  "LayoutVersion": 1,
  "PublicKey": "<RSAKeyValue>...</RSAKeyValue>"
}
```

Validation requirements:

- `Version` must be a supported semantic/numeric version string;
- `RuntimeIdentifier` must match an enabled release target;
- `Channel` must be 1-32 ASCII letters/digits/hyphen/underscore and allow-listed (`development`, `stable`, and any intentionally added channel);
- `ExecutableHash` must be exactly 64 hexadecimal characters;
- `LayoutVersion` must be a supported positive integer;
- `PublicKey` must pass the same length/XML/RSA checks as the existing server-list bootstrap.

For an already-known sender, verify with the stored player public key and reject a different supplied key. For a genuinely new sender, use the same enrollment rules as `LauncherServerList`: verify the request signature with the supplied public key, bind it to the authenticated device/account record, and grant no extra authorization from that key alone. This lets a fresh V3 installation check for a critical launcher update before its first server-list refresh. Reject bad signatures before looking up release data.

Do not authorize administrator behavior from the requested channel. Development-channel access should be controlled server-side with an explicit device/account allow-list during testing.

## 3. Response envelope

Return HTTP 200 and `application/json`. Both update and no-update responses are signed offline and have the same envelope:

```json
{
  "payload": "base64 of exact UTF-8 manifest JSON bytes",
  "signature": "base64 RSA-SHA256 PKCS#1 v1.5 signature over those exact bytes",
  "keyId": "sunshine-release-2026-01"
}
```

Do not parse and reserialize an envelope generated by the release script. Return the stored envelope bytes unchanged. The client verifies `signature` before parsing `payload`.

Keep the decoded payload below 64 KiB and the whole HTTP response small; the client rejects empty/oversized manifest payloads and implausible RSA signature lengths.

An update payload has this schema:

```json
{
  "schemaVersion": 1,
  "updateAvailable": true,
  "releaseId": 42,
  "version": "3.1.0",
  "runtimeIdentifier": "win-x64",
  "channel": "development",
  "minimumVersion": "3.0.0",
  "publishedUtc": "2026-08-19T12:00:00.0000000+00:00",
  "package": {
    "url": "https://sunshinealley.games/launcher/releases/3.1.0/win-x64/SunshineAlleyLauncher.exe",
    "size": 123456789,
    "sha256": "64 lowercase hex characters"
  }
}
```

A no-update payload is also signed:

```json
{
  "schemaVersion": 1,
  "updateAvailable": false,
  "releaseId": 42,
  "version": "3.1.0",
  "runtimeIdentifier": "win-x64",
  "channel": "development",
  "minimumVersion": "3.0.0",
  "publishedUtc": "2026-08-19T12:00:00.0000000+00:00",
  "package": null
}
```

Never return a blank body, HTML error page, bare URL, or literal `OK` from the V3 operation.

## 4. Server-side selection algorithm

Store one active release per `(channel, runtimeIdentifier)`. A minimal handler is:

```text
authenticate signed launcher request
validate request fields
load active release for requested channel + RID

if no active release:
    return a controlled API error; client continues without updating

if request version >= active version OR request executable hash == active SHA-256:
    return exact bytes of active no-update.envelope.json

if request version < active minimumVersion:
    return a controlled error directing the client through the bridge release

return exact bytes of active update.envelope.json
```

Use a real version parser; do not compare versions lexically. `3.10.0` is newer than `3.9.0`.

The client independently rejects:

- a different RID or channel;
- a non-newer version;
- a replayed/lower `releaseId`;
- an invalid manifest signature;
- an unapproved URL host or non-HTTPS URL;
- a package with the wrong size or SHA-256;
- a production Windows EXE that fails Authenticode verification.

After an early-startup rollback, the client records the failed `releaseId` and will not retry that ID or a lower one. Publish the fix with both a higher version and higher release ID.

## 5. Recommended release storage

Use immutable, versioned public paths:

```text
/srv/sunshine-alley/launcher/releases/
└── 3.1.0/
    └── win-x64/
        ├── SunshineAlleyLauncher.exe
        ├── update.envelope.json
        ├── no-update.envelope.json
        └── server-release.json

/srv/sunshine-alley/launcher/active/
├── development-win-x64.json
└── stable-win-x64.json
```

Expose only the release executable through the public HTTPS path. Envelope files may be returned by the API from non-public storage. `server-release.json` is deployment metadata, not a client response.

Example active record:

```json
{
  "channel": "development",
  "runtimeIdentifier": "win-x64",
  "releaseDirectory": "/srv/sunshine-alley/launcher/releases/3.1.0/win-x64",
  "releaseId": 42,
  "version": "3.1.0"
}
```

Activate a release by atomically replacing only this small active record after all immutable files are present and verified. Do not overwrite an existing version directory in place.

## 6. Deployment procedure

The release operator produces the four files with `scripts/windows/Publish-WindowsUpdate.ps1`; see `WINDOWS_RELEASE.md` for signing and publishing.

On the API/static-file server:

1. Create a new immutable version/RID directory.
2. Upload `SunshineAlleyLauncher.exe`, both envelope files, and `server-release.json`.
3. Recalculate the executable SHA-256 and size on the server.
4. Compare them with `server-release.json` and the decoded, signature-verified update payload.
5. Confirm the executable is served as bytes without compression/transformation.
6. Confirm the public URL is HTTPS and stays on `sunshinealley.games`; redirects to another host are rejected by the client.
7. Call the new API as an allow-listed development device and verify the exact stored envelope is returned.
8. Download the public EXE URL and verify its hash again.
9. Atomically point `development-win-x64.json` at the new directory.
10. After the complete Windows test matrix passes, repeat activation for `stable` using a production-signed release.

Do not place the offline manifest private key on the API or web server. The server only stores pre-signed envelopes. Compromise of the API database alone must not permit creation of a trusted launcher release.

On a Linux API host with `jq`, `base64`, and OpenSSL, an operator can independently verify the stored update envelope using the repository's public PEM (never the private PEM):

```bash
jq -r .payload update.envelope.json | base64 -d > payload.json
jq -r .signature update.envelope.json | base64 -d > signature.bin
openssl dgst -sha256 -verify update-public-key.pem -signature signature.bin payload.json
sha256sum SunshineAlleyLauncher.exe
stat -c %s SunshineAlleyLauncher.exe
```

Compare the payload's `sha256` and `size` with the last two outputs and `server-release.json`. Remove the temporary decoded payload/signature after validation; they contain no secret but should not become alternate deployment inputs.

## 7. Development-channel test without affecting players

Use a release built with:

```powershell
./scripts/windows/Publish-WindowsUpdate.ps1 `
  -Version 3.0.1 `
  -ReleaseId 1 `
  -Channel development `
  -PackageBaseUrl https://sunshinealley.games/launcher/releases `
  -DevelopmentUnsigned
```

In the installed test launcher settings file:

```text
%LOCALAPPDATA%\Sunshine Alley\Config\settings.json
```

set:

```json
"Updates.Channel": "development"
```

Restrict the server's development channel to the test device/account. Production V2 launchers never call `LauncherGetUpdateV3`, and the legacy endpoint remains unchanged.

`-DevelopmentUnsigned` disables only the client-side Authenticode requirement at compile time. The manifest must still have a valid release signature and the package must still match its signed SHA-256. Never activate such a build on `stable`.

## 8. V2-to-V3 bridge rollout

After V3 installation, migration, updating, rollback, repair, and uninstall are validated:

1. Build a production-signed V3 bridge with the permanent embedded release public key.
2. Keep that exact raw EXE at an immutable URL indefinitely.
3. Test it with an isolated/staging build of V2 first.
4. Update the legacy hash table/logic so recognized older V2 hashes receive the bridge EXE URL.
5. Continue returning `OK` for the bridge hash so an old updater cannot loop.
6. The bridge migrates into `App`, `Config`, and `Data`, then checks `LauncherGetUpdateV3` for the newest V3 release.

For users who do not launch V2 until next year, the legacy endpoint and bridge URL must still exist and retain compatible TLS/HTTP behavior.

## 9. Rollback policy

Client rollback restores the exact previous executable when a new process exits before startup confirmation. Server rollback is different: clients reject lower versions and previously accepted/lower release IDs.

For an emergency server-side rollback, rebuild the previous known-good source as a new higher version and higher `releaseId`, sign it normally, and activate that new release. Do not point `active` at an older manifest.

## 10. Logging, rate limiting, and monitoring

Log only operational metadata needed for support:

- request time;
- authenticated account/device record ID (not private keys or request signatures);
- current version/hash prefix;
- requested RID/channel;
- selected release ID/version;
- outcome and HTTP status.

Rate-limit update checks per authenticated identity and IP. Alert on repeated invalid signatures, unknown RIDs/channels, unexpected executable hashes, failed static-file hash checks, or a missing active release. Never log manifest private-key material, Windows Credential Manager secrets, or full player RSA material.

## 11. Key rotation

The first implementation trusts `sunshine-release-2026-01`. Before rotating it, ship a normally signed transitional launcher that trusts both the old and new public keys, wait for adoption, then begin signing envelopes with the new key ID. Never replace the embedded public key and server signature simultaneously without a trust-overlap release.
